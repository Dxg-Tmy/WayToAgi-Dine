# 麦点点 · 点餐流程与文案设计（v2，过程稿）

> ⚠️ 本文是 21:19 的设计稿，仅作过程留档。**最终实现见 [`flow-as-built.md`](flow-as-built.md)**。
> 主要差异：本稿含「上一步」回退且用「下一个/确定/完成」三键；最终版按用户定调**去掉回退**，改为「▼下一个 / ▲上一个 / 确认」（长按确定结算）。

> 目标：聋哑 / 低视力 / 识字困难用户，用最少按键完成一次点单。  
> 原则：**任何时刻最多 3 个候选、循环高亮、可回退**；不堆 59 项长列表。  
> 本稿只定逻辑与文案，不含代码。

## 0. 先回答你提的两个问题

### 问题 1：二维码太大、显示不全

- 原因：支付面板里的 `<canvas class="qr" width="300" height="300">` 固定 300×300，在窄面板 / 小屏里溢出被裁。
- 修法（UI，不涉及流程）：`qr` 改为 `width:100%; max-width:min(220px,60vw); aspect-ratio:1; height:auto`，面板 `max-height:90vh; overflow:auto`，二维码永远完整可见、居中。真码 `<img>` 与模拟 `<canvas>` 同一套尺寸规则。
- 结论：这是个纯 CSS 尺寸 bug，改一次即可，**不影响下面的流程设计**。

### 问题 2：交互不友好

拆成三条，用新流程逐条解决：

| 你提的问题                 | 新流程怎么解决                                              |
| --------------------- | ---------------------------------------------------- |
| (a) 50~60 项点“下一个”点到崩溃 | 不再顺序遍历全菜单。开场先分流「主食/小吃/饮料」，每层最多 3 个候选，**3~5 次按键到结算**。 |
| (b) 没有“上一步”           | 每个节点记录上一步状态+高亮位置，随时回退；三键硬件用「长按下一个」或加第 4 键（见 §5）。     |
| (c) 没有时段引导            | 开场按时段问候，午餐/晚餐直接先问主食，不绕弯。                             |

## 2. 状态机与逐节点文案

符号：`【下一个】`切候选并高亮、`【确定】`选中、`【完成】`= 前进/结算、`【上一步】`回退。语音与屏幕文字**同一句**（聋哑看字、低视力听声）。

### N0 开场 · 时段问候

按本地时间判断时段：

- 早餐 05:00–10:29 / 午餐 10:30–13:59 / 下午茶 14:00–16:59 / 晚餐 17:00–20:59 / 夜宵 21:00–04:59

文案（随时段）：

- 午餐：「现在是中午，**先来点主食，还是来点小吃？**」
- 晚餐：「现在是晚上，**先来点主食，还是来点小吃？**」
- 早餐：「早上好，**来个早餐主食，还是来点小食？**」
- 下午茶/夜宵：「现在是下午茶/夜宵，**来点小吃，还是来杯饮料？**」

候选（循环高亮，3 选）：

- 午餐/晚餐：`①主食　②小吃　③饮料`
- 下午茶/夜宵：`①小吃　②饮料　③主食`

操作：`下一个`切高亮 → `确定`进入对应分支；此节点无上一步。  
→ 主食走 N1A；小吃走 N1B；饮料走 N1C。

### N1A 主食类型

- 文案：「**主食有：汉堡、炸鸡、鸡肉卷。要哪一类？**」
- 候选：`汉堡 / 炸鸡 / 鸡肉卷`
- 若某类缺货（如本店无独立卷）：该项置灰并播报「鸡肉卷今天没有」，`下一个`自动跳过。
- `确定` → N2A（该类型的推荐前 3 款）

### N2A 主食·前 3 款（循环高亮）

- 文案（示例·汉堡）：「**汉堡卖得最好的三款。第一款：双层吉士汉堡，25 块。按下一个看下一款。**」
- 显示：大图 + 名称 + 价格，**当前款高亮/放大**，其余淡化；顶部「第 x / 3 款」。
- 循环：`下一个` 1→2→3→1；`上一步`回 N1A。
- `确定` → 选中该款 → N3（饮料）
- 前 3 款来源见 §4「排序规则」。

### N1B 小吃类型

- 文案：「**小吃有：薯条、鸡块、鸡翅。要哪一类？**」
- 候选循环 → 该类型前 3 款（同 N2A 交互）→ 选中 → N3（饮料）

### N1C 只要饮料

- 直接 → N3（无主食，不触发套餐匹配）

### N3 饮料 · 断言式推荐

- **非冬季**：「**主食有了，我们来一杯可乐吧。**」（主食为小吃时：「**再来一杯可乐吧。**」）
- **冬季**：「**天气冷，我们来一杯锡兰红茶吧。**」
- 候选循环（`下一个`＝换一个，高亮切换）：
  - 非冬季：`可乐 → 雪碧 → 多汁柠柠 → 黄金橙橙 → 可乐`
  - 冬季：`锡兰红茶 → 鲜萃咖啡 → 浓浓黑巧(热) → 可乐 → 锡兰红茶`
- 操作：`确定`＝接受当前（要得）；`下一个`＝换一个；`完成`＝不要饮料（→ N5 结算）。
- 接受且有主食 → N4（套餐匹配）；无主食 → N5。

> 措辞红线（按你的要求）：
>
> - ✅「我们来一杯可乐吧。」
> - ❌「要不要来一杯可乐？」「来一杯可乐好不好？」——**禁用“要不要 / 好不好 / 行不行”**，直接给结论。

### N4 套餐匹配（仅在“主食 + 饮料”都成立时）

- 匹配逻辑：在套餐类商品里，找**名称包含所选主食关键词**的套餐。
  - 例：选「双层吉士汉堡」→ 命中「双层吉士汉堡套餐 ¥39.5」
  - 选「麦香鱼」→「麦香鱼套餐 ¥37.5」；选「麦辣鸡翅」→「麦辣鸡翅4块套餐 ¥42」；选「麦乐鸡」→「麦乐鸡套餐 ¥29.5」
- 命中 1 个：「**你选的{主食}有个更划算的套餐：{套餐名}，{价}。要换成这个吗？**」→ `确定`换 / `完成`不换
- 命中 2~3 个：循环高亮让选（同 N2A 交互）
- 命中 0 个：静默跳过 → N5
- 选中套餐 → 用套餐替换单品（或加购）→ N5

### N5 结算确认

- 文案：「**一共 {n} 件，合计 {¥}。按确定去支付。**」
- 显示清单（名称×数量×小计）+ 合计
- `确定` → N6；`上一步` → 回 N4/N3

### N6 支付

- 二维码**自适应尺寸**（见 §0 问题1），居中不裁切
- 「我已支付」/「取消」

### N7 完成

- 显示取餐码 / 订单号；任意键 → 回到 N0 新一单

## 3. 交互铁律（贯穿所有节点）

1. **每屏最多 3 个候选**，`下一个`循环 3→1，当前项高亮（放大+描边+语音报名称价格）。
2. **上一步**：每个节点存 `{state, cursor, 临时购物车快照}`，回退后恢复原高亮位置。
3. **不展示 59 项长列表**；「看全部菜单」只放在协助者设置里，不作为主路径。
4. **断言式表达**：给结论不给疑问，减少“要不要”带来的犹豫。
5. 语音与文字一致；图片加载失败时用大字品类占位，信息不丢。

## 4. 排序规则（“卖得最好的 3 款”）

MCP `query-meals` **不返回销量/排名**，只有 `tags`（爆款 / 人气 / 超值 / 上新）。所以：

- 默认排序权重：`爆款 3 > 人气 2 > 超值 1 > 上新 0.5 > 普通 0`，同分按菜单原顺序。
- **允许人工置顶**：在缓存文件里给每个类型维护一个 `top3` 覆盖数组，优先级最高（你想让哪三款当门面就写哪三款）。
- 结果缓存进 `menu` 快照，前端直接读，不再实时算。

## 5. 三键硬件怎么“上一步”

硬件只有「下一个 / 确定 / 完成」三键，加回退有两种方案，需你选：

- **方案 A（不加硬件）**：长按【下一个】≥ 800ms 触发上一步（固件需配合，另一 agent 改）。
- **方案 B（加第 4 键）**：新增「上一步」实体键，语义最清晰，但改外壳/固件。
- **Web 端**：无论 A/B，都加屏幕「上一步」按钮 + 键盘 `Backspace/←`。

## 6. 需要你拍板的 5 件事（这些定了我才动手）

1. **主食三分类**：本店「鸡肉卷」无独立单品，是否改成「汉堡 / 炸鸡 / 其他」，或把「学生专享汉堡小食随心选」当卷类？还是保留“鸡肉卷”并显示缺货？
2. **前 3 款怎么定**：用标签权重自动排，还是你直接给我每个类型的三款名单（更可控，推荐）。
3. **套餐匹配精度**：先按“名称含主食关键词”粗匹配（0 额外调用）；还是要对候选套餐调 `query-meal-detail` 精确核对成分（每个套餐多 1 次 MCP 调用，最多 3 次）？
4. **冬季判定**：MCP 无天气，用月份（11–2 月＝冬季）够不够？还是要接实时天气/`now-time-info`？
5. **上一步**：硬件走方案 A（长按）还是 B（第 4 键）？
